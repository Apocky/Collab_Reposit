# Spec issues found by the Rust vertical slice

Collected from implementing agents. The canon-gap triage resolves each one.

- NOTE TO ORCHESTRATOR: the user asked to be asked clarification questions for every system. I am a subagent and cannot ask them, so each item below marked QUESTION should be put to the user. Every canon §21 vector in scope reproduced exactly: tests 1-9, 11 and 12, test 21, all 40 rows of the §13.8 table, the doc 02 §4.3 spot values and BLAKE3 hash d2612a42..., and every doc 02 §4.4 and §4.6 worked example.
- Doc 02 §4.6 (revision committed in ed38b6b), closest_seg_seg: the `.expect("invariant: div256 range")` and `div128 range` panics are not true invariants, even inside the 512 m range the doc says is safe. Case 1: nearly parallel segments p1=(0,0,0), q1=(1,0,0), p2=(5,1,0), q2=(6 m, 1 m + 1 raw, 0). The unclamped s is about -2^32, so div256 panics. Case 2: a point against a segment 1 raw long, 5 m away. Then div128(f, e) is 5*2^32 m and does not fit Fx. I implemented clamp-before-narrow in 256-bit arithmetic. A property test compares this against a literal transcription of the doc code and the results are identical wherever the doc code completes. Both cases are unit tests in geom::tests::closest_seg_seg_where_doc_code_panics. QUESTION: should doc 02 adopt the clamp-first form?
- Doc 02 §4.6 div128 and the older `num << 32`, plus a canon §1.3 caveat: in Rust, `<<` is not covered by overflow-checks and drops high bits silently. So `floor_div_i128(n << 32, d)` wraps silently when |n| >= 2^95, which breaks the 'overflow panics' guarantee. I implemented the shift as a checked multiply. Canon §1.4 `Fx::from_int(n) = (n as i64) << 32` is exact only because doc 02 makes n an i32. QUESTION: should the canon state that every `<< k` in a normative formula is a checked multiply by 2^k?
- Doc 02 §3.3 contradicts §4.1 and §4.7. §3.3 lets the math crate depend only on blake3, but §4.1 and §4.7 have Fx and Rng derive serde Serialize/Deserialize. I added an opt-in `serde` feature, off by default, and Rng::state() and from_state() for saves that do not use serde. QUESTION: which rule wins, and should canonical save serialization (doc 02 §6.5) use serde?
- Canon §1.9 fwd is ambiguous about where the minus sign goes. `(-sin)*cos >> 30` (negate first) and `-((sin*cos) >> 30)` differ by 1 raw when the product is not a multiple of 2^30. Example: fwd(8192, 8192).x is -536870913 negate-first and -536870912 shift-first. I implemented negate-first, as the formula is written. QUESTION: please confirm, and add a vector to §21.
- Canon §1.9 fwd(yaw, pitch): the type of pitch and whether fwd clamps it are unspecified. I implemented fwd(yaw: Bam, pitch: i16). Pitch is reinterpreted as u16 for sin_bam and cos_bam, fwd does no clamping, and clamp_pitch, pitch_from_bam and pitch_as_bam are provided as helpers. QUESTION: should fwd clamp to ±16000 itself?
- Canon §13.8 says 'Every table uses d_pow = min(d, 300)', but S takes a level, not a depth. I applied the cap to S as well, so S(301) = S(300) = 99,700. The domain for d = 0 is also undefined; it panics in my code. QUESTION: does the cap apply to S, and are ilvl and depth always >= 1 and u32?
- Canon §13.8 and §1.2: P, T and H are i64 Bp multipliers, but canon §1.3 mul_bp takes `bp` without saying its width. I added mul_bp_wide(x: i64, bp: i64) for `base × P(d)`. QUESTION: is `base × P(src_lvl)` (§10.4, §13.8.1) exactly floor(base*P/10000), i.e. mul_bp?
- Canon §3.1 range_incl: the reference body computes `hi - lo + 1` in i64. With overflow-checks on, that panics for spans above i64::MAX, which the function's own assert allows (up to u64::MAX - 1). I compute the span in i128. A property test confirms identical results wherever the reference does not panic.
- Canon §1.3 ceil_div = -floor_div(-a, b) overflows at a = i64::MIN. I implemented the equivalent non-negating form, which gives identical results for every other a and is also defined at i64::MIN.
- Canon §1.4 dist2 says 'never narrow it', but even the i128 sum can overflow at extreme Fx: one axis at Fx::MAX vs Fx::MIN gives (2^64-1)^2 > 2^127. It is checked and panics deterministically, and it cannot happen inside the Folio box. QUESTION: should the canon state a coordinate range, for example |raw| < 2^62, for dist2 and dot_wide?
- Canon §3.6 decode leaves several things unspecified. (1) Characters outside the alphabet other than U, such as '!', Crockford check symbols *~$=, tabs, newlines or non-ASCII: I reject them. (2) Whether whitespace other than ASCII space is stripped: I strip only '-' and ' '. (3) Error precedence: I check length, then U, then alphabet, then first char above F. QUESTION: confirm these rules, or should decode also accept lowercase-only input and whitespace like tabs?
- Canon §3.6 daily and weekly seeds do not say whether the date string is validated. I implemented strict validation. Daily must be YYYY-MM-DD with a real calendar date and year 0001-9999. Weekly must be YYYY-Www with W uppercase and the week no higher than that year's ISO week count. I also added iso_week(y, m, d) and weekly_seed_for_date; ISO week math was cross-checked against Python's datetime. My computed vector is weekly_seed("2026-W41") = 0x2e7e2bae906b8339, and 2026-10-11 falls in ISO week 2026-W41. QUESTION: should invalid strings be rejected or hashed as-is, and should a canonical weekly-seed vector be added to §21?
- Doc 02 §4.6 DDA states no max-steps bound, only the contract t_max < 2^62. The iterator takes max_steps, the number of steps after the start block, so it yields at most max_steps + 1 items. It also ends cleanly at the i32 block-range edge instead of overflowing `cell[ax] += step[ax]`, and keeps an overflowing t_next at Fx::MAX. Within the doc's contract the results are identical. QUESTION: what max-steps value should doc 03 use, for example 3*ceil(t_max) + 3?
- Doc 02 §4.6 treats tangent rays inconsistently. ray_sphere treats h == 0 as a miss (`h <= 0`), while the ray_capsule body path misses only on h < 0. I implemented both exactly as written. QUESTION: is that intended?
- Doc 02 §4.6 I256 API lists `pub fn cmp(self, o: I256) -> Ordering` as an inherent method. I implemented ordering through derived Ord instead, called as `a.cmp(&b)`, because an inherent cmp would shadow Ord::cmp; the derived order on (signed hi, unsigned lo) is exactly numeric order. Doc 02 §4.3 also gives the path `crates/math/src/trig_table.rs`, but the workspace path is crates/palimpsest_math/src/trig_table.rs.
- Doc 02 §4.4 accuracy claims were re-measured and hold. Over 300,000 random inputs (2^10 to 2^62) the worst error is 0.8165 Bam against the stated 0.818. Over the -40..=40 grid it is 0.7879 against 0.788. The isqrt_u128 bound of at most 7 passes also holds. QUESTION: is the ±1 Bam atan2_bam contract enough for AI aim and yaw_from_dir, or do you want a correctly rounded atan2?
- Doc 02 §4.7 says 'Debug builds count draws per stream in a side table'. I did not implement this in the math crate: Rng has no stream identity, and a debug-only side table would change behaviour between profiles. QUESTION: should the sim crate own this counter?
- QUESTION (hash): blake3_256(parts) hashes the plain concatenation with no length prefixes, so ["ab","c"] and ["a","bc"] collide. That is fine for the canonical state serialization, but any caller hashing several variable-length fields should length-prefix them. Should the canon say so?
- QUESTION (fx): display rounding for Fx-derived quantities such as distances is not in canon §1.5, which covers only Milli and Bp. Fx Debug and Display use round-half-even milli; simulation code uses to_milli_floor. Which rule should the UI use?
